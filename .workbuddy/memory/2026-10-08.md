## 在 GitHub 上生成 Docker 镜像（CI 构建并发布到 GHCR）

### 背景：远端已有一个「假」工作流

远端 `main` 此前是用户在 GitHub Web UI 上点出来的 Docker 入门模板（提交 `20c197f`
「Add Docker Image CI workflow」，本会话先 `git pull --ff-only` 合进来）。它只做
`docker build . --tag my-image-name:$(date +%s)`：**不推任何 registry、不打有意义的标签**，
所以外部拿不到镜像。已替换为真正发布镜像的工作流。

### 交付

`.github/workflows/docker-image.yml` 重写：

- **build 作业**：`docker/build-push-action@v6` 推 `ghcr.io/czleexy/webterm`，
  标签 `latest` / `main` / `sha-<full>` / 语义版本（打 `v*` 时）
- **smoke 作业**：`docker pull` → `docker run -p 8080:8080` → 等 `/api/health`
  → 断言首页 `text/html` 且含 `id="root"` → 比对镜像内版本与 `package.json`
  —— 这条正对阶段 9 的验收条件，以后由 CI 出证据
- **平台策略**：常规 push 只 `linux/amd64`；`v*` 标签或手动触发才 `amd64+arm64`
- PR 只构建不推送且只 amd64；`provenance: false`；GHA 远程缓存；文档走 `paths-ignore`
- 权限 `packages: write`（build）/ `packages: read`（smoke）

新增 `.gitattributes`：`*.yml` / `*.yaml` 固定 `eol=lf`。

### 落地前校验（`data/tmp/check-workflow.py`，47 项全过）

真 YAML 解析 + 结构核对 + **联网确认每个 `uses:` 的版本标签存在** + 对每段 `run:` 做 `bash -n`。

两个踩到的坑值得记住：

1. ⚠️ **校验要读入库形态（`git show :path`），不是工作区文件**。Windows + `core.autocrlf=true`
   下磁盘上全是 CRLF、blob 里是 LF；拿工作区文件跑 `bash -n` 会得到一串假的 `$'\r'` 语法错
   （`unexpected token $'do\r'`），看着像真 bug。
2. ⚠️ **Python `subprocess` 的 `text=True` 在 Windows 上会把 `\n` 翻成 `\r\n`** ——
   即使输入是干净的 LF，喂给 bash 也会变成 CRLF。喂脚本必须传 bytes。

顺带确认了环境里真实的 node 版本目录是 `22.12.0` 与 `22.22.2-6`
（备忘里原先写的 `22.22.2-3` 已失效，已修正）。

### 本轮新增的排障能力
